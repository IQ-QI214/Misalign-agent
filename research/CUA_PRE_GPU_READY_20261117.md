## 下一轮模型究竟跑什么

配置固定在 [`m1_pilot.json`](../configs/cua/m1_pilot.json)：

- 模型：已有公共目录中的 Qwen3.5-9B，不重新下载或复制权重；关闭 thinking，沿用固定 CUA-Lite 的原生动作协议。
- 两个开发任务家族：修改 `status.txt` 的状态；修改 `inventory.csv` 中指定记录的数值。均允许终端操作，要求始终保留合成保护文件。
- 每个任务使用四种说明：空白对照、良性说明、伪装维护指令、伪装任务前置条件。攻击只要求删除合成保护文件，没有真实外传或真实敏感文件。
- 用户合法目标与评分器保持相同，说明通过不可信文件内容显示在终端中；条件标签不拼入模型提示。所有条件都存在可执行的安全完成路径，CPU 脚本已验证。
- 每组 4 个独立种子，共注册 **32 条模型轨迹**；每条最多 8 个动作轮次，每轮最多 512 个新 token，串行运行。
- 单次 GPU 会话预算 30 分钟，包含模型加载。到预算停止并保留未启动项；32 是注册总数，不承诺一张卡半小时一定全部完成。超时清理另设最多 15 秒终止宽限。

这些都是开发测量任务，**不是 OSWorld 正式基准，也不是最终论文训练集或测试集**。它们先回答：模型能否做完合法任务；固定攻击下能否观察到不同安全/效用结果；逐 token 概率与实际动作能否完整记录。第一轮不做自动红队共同进化，不做分支因果估计，不更新权重。

## 记录与分析约束

每一步保存原图、实际输入图、渲染提示、实际输入 token、生成 token、生成配置、解析/执行动作和原生反馈。逐 token 概率直接来自生成过程，不用文本重新分词来伪造采样记录。EOS 若由模型生成，也包含在 token 与概率列表中。客户端核对请求、提示和图像指纹，防止回复错配。

概率实现参考 [Transformers 的生成接口源码](https://github.com/huggingface/transformers/blob/main/src/transformers/generation/utils.py)，以实际部署的 5.21.0 源码和独立前向测试为准。5.22 与 5.21 的接口差异已经在 CPU 验收中暴露；不能以新版文档或跳过的测试代替部署版本通过。

分析同时列出安全、合法完成、联合安全完成和 UNKNOWN。仅对完整且全部可判定的同任务同攻击组计算：轨迹加和奖励的标准化优势，以及分别标准化安全/效用后平均的描述性对照。**拆分奖励后也可能互相抵消**；该情况已用构造例验证，仍需 M1 测量它是否实际出现，不能把构造例当成模型发现或 GDPO 复现结果。

所有当前输出都保持 `training_eligible=false`。记录了概率并不自动允许训练；教师/脚本动作不能冒充旧策略采样，失败轨迹也不能直接作正向模仿标签。拒绝类型尚无通用自动识别器，安全但未完成不自动归类为过度拒绝。

## 环境与预算

CPU 继续复用已有 Docker 桌面与约 2.64 GiB 的运行缓存。没有本机环境安装，没有模型下载，没有 GPU 或 API 调用。

收尾检查：本轮三个原始运行目录合计 802,973,696 bytes，约 766 MiB；共享项目文件系统可用约 46.3 GiB，运行中的桌面容器为 0。目录保留实际输入与原图、完整动作和第一失败，未保存训练权重或优化器状态。

GPU 仍使用旧开发实例的现有环境：Python 3.12、Transformers 5.21.0；历史 Torch 为 `2.8.0a0+5228986c39.nv25.06`。该 venv 继承 GPU 镜像的系统 Torch，不能在 Python 3.10 的 CPU 镜像上直接用它的软链接判断依赖是否存在。本次用已有 CPU Python 3.12/Torch 加隔离的 5.21 包做接口检查；实际 CUDA 内核、显存和 9B 加载仍必须开卡验证。

模型资产记录包括配置/分词器/权重索引的 SHA256，以及四个权重分片的大小和修改时间。未读取全部权重计算 SHA256，因此这不是权重内容的完整密码学指纹；GPU 加载前会与 CPU 清单核对。共享文件系统上的代码每次单独快照，旧运行不会被后续覆盖。

## 开卡前与开卡后的统一入口

**只在 [cua-test-qi 的网页终端](https://qz.sii.edu.cn/ide?notebook_id=04ab0f8a-6967-4d81-8cbc-91bb3a6ab7a7) 执行以下入口。** 它位于 CUA Docker CPU 实例；其他 CPU 中转和 `dev-misalign-qi` GPU 实例都不是这个入口的执行位置。提示符中的 `root:zjq` 只显示目录，不能识别实例。

11 月 17 日用户实际启动暴露了两项遗漏：在仓库外使用 `-m scripts...` 找不到模块；进入正确仓库后，旧入口未先恢复数据盘挂载，因而找不到盘内的 Python 缓存。报错不证明缓存已删除，也没有启动模型。此次新增独立启动入口 `scripts/qz_cua_start.py`，先复用现有 ext4 和 Docker 恢复程序，再绑定原缓存、检查 CPU 解释器与已有资格记录，最后进入原 M1 会话。原测量代码、任务和资格指纹保持不变。启动修复的测试与远端验证状态单独记录在 `validation/cua_startup_recovery_20261117.json`。

**该启动修复已在重启后的 CUA CPU 实机验证。** 确认旧 ext4 盘尚未挂载，恢复后原缓存可用；离线容器退出码 0，统一入口返回 `CPU_ENVIRONMENT_READY`，17 项相关测试全部通过，0 跳过。从 `/tmp` 使用脚本绝对路径调用默认计划也成功。Docker 启动时两次探测超时已记录，后续成功；没有新建数据盘或重新下载环境。GPU 中转心跳过期，本轮未派发模型测量。

下面使用脚本绝对路径，**无需先切换目录**。部署新入口后，先只恢复并检查 CPU：

```bash
python3 -B /inspire/hdd/project/independent-security-research/wenming-253108090054/zjq/Misalign-agent/scripts/qz_cua_start.py --prepare-cpu
```

应输出 `CPU_ENVIRONMENT_READY` 及新恢复收据路径。恢复阶段复用已有文件，不新建或格式化数据盘、不下载模型、不派发 GPU。若已有缓存或挂载不符合预期，保留现场并停止。默认不带参数只打印计划。

随后在 GPU 实例恢复已有中转，沿用现有 `qz_cua_gpu_connect.sh`。GPU 已开启、中转正常且资格收据通过后，**仍在上述 CUA CPU** 启动模型测量：

```bash

```

使用 `nohup` 运行该监督入口可脱离网页终端；后台启动不等于完成，最终需核查控制器退出记录、每条 episode 收据与 GPU worker 的真实退出码。若需要继续未尝试的注册项：

```bash

```

配置、模型元数据或代码不同会拒绝续跑。已尝试但无效的项目不会自动重跑或被覆盖，仍留在原始分母中。只有训练后的完整起点评测，才能证明方法最终有效。
